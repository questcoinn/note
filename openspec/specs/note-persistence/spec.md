# note-persistence Specification

## Purpose

노트 원문과 수정 시각을 사용자의 브라우저에 자동으로 저장해, 새로고침하거나 창을 다시 열어도 편집한 내용이 남아 있게 한다. 저장 시점, 저장 상태 전이, 실패와 손상된 데이터 처리를 정의한다.

## Requirements

### Requirement: 편집한 노트는 새로고침 후에도 유지
저장이 끝난 노트의 원문과 수정 시각은 같은 브라우저에서 새로고침하거나 창을 닫았다 다시 열어도 그대로 복원되어야 한다(SHALL). 제목, 미리보기 문장, 미리보기는 복원된 원문에서 다시 파생한다. 노트 데이터는 사용자의 브라우저 안에만 저장하며, 저장을 위해 네트워크 요청을 보내지 않아야 한다(MUST NOT).

#### Scenario: 새로고침 후 편집 유지
- **WHEN** 사용자가 노트 A의 원문 끝에 `## 새 섹션`을 입력하고 저장 상태가 "저장됨"이 된 뒤 페이지를 새로고침한다
- **THEN** 노트 A를 열면 원문과 미리보기에 "새 섹션"이 그대로 있다
- **AND** 목록에서 노트 A 카드의 제목과 미리보기 문장이 편집한 원문을 반영한다

#### Scenario: 저장 중 네트워크 요청 없음
- **WHEN** 사용자가 원문을 편집하고 저장이 일어난다
- **THEN** 저장을 위한 네트워크 요청이 발생하지 않는다

### Requirement: 첫 실행 초기 데이터
저장된 노트가 하나도 없는 상태로 앱을 열면 앱에 포함된 목업 노트를 표시하고, 그 노트들을 저장해야 한다(SHALL). 이때 각 목업 노트의 수정 시각은 앱을 연 시각을 기준으로 정해, 첫 화면의 수정 시각 문구가 목업에서 의도한 문구("3분 전", "어제" 등)와 같게 보여야 한다(SHALL). 저장된 노트 항목이 하나라도 있으면(읽을 수 없는 항목 포함) 목업 노트를 다시 적용하지 않고 저장본만 사용해야 한다(MUST).

#### Scenario: 처음 연 앱
- **WHEN** 저장된 노트가 없는 브라우저에서 앱을 연다
- **THEN** 목업 노트 전체가 목록에 보이고, 첫 번째 카드의 수정 시각 문구는 "3분 전"이다
- **AND** 페이지를 새로고침해도 같은 노트들이 보인다

#### Scenario: 저장본이 목업보다 우선
- **WHEN** 사용자가 목업 노트 A의 제목을 고치고 저장된 뒤 새로고침한다
- **THEN** 노트 A는 목업의 원래 제목이 아니라 고친 제목으로 보인다

### Requirement: 자동 저장 시점
원문을 편집하면 별도 조작 없이 저장되어야 한다(SHALL). 입력이 약 0.5초 멈추면 저장하고, 멈추지 않고 계속 입력하는 동안에도 약 2초마다 한 번은 저장해야 한다(SHALL). 노트마다 따로 저장하며, 한 노트의 저장이 다른 노트의 원문이나 저장 상태를 바꾸지 않아야 한다(MUST NOT).

#### Scenario: 입력을 멈추면 저장
- **WHEN** 사용자가 원문에 글자를 입력하고 1초 동안 아무것도 입력하지 않는다
- **THEN** 저장 상태가 "저장됨"이 되고, 이때 새로고침하면 입력한 글자가 남아 있다

#### Scenario: 계속 입력해도 주기적으로 저장
- **WHEN** 사용자가 5초 동안 쉬지 않고 원문에 입력한다
- **THEN** 입력이 끝나기 전에도 저장이 일어나, 그 사이 새로고침하면 적어도 약 2초 전까지 입력한 내용은 남아 있다

### Requirement: 즉시 저장 계기
저장을 기다리는 편집이 있을 때 다음 경우에는 대기 시간을 기다리지 않고 바로 저장해야 한다(SHALL): 탭이나 창이 가려질 때, 페이지를 떠날 때, 다른 노트를 열거나 노트 선택을 벗어날 때, 사용자가 `Cmd+S`(macOS) 또는 `Ctrl+S`를 누를 때. 저장 단축키는 브라우저의 "페이지 저장" 동작을 열지 않아야 한다(MUST NOT).

#### Scenario: 입력 직후 탭 닫기
- **WHEN** 사용자가 원문에 글자를 입력하고 곧바로 탭을 닫은 뒤 앱을 다시 연다
- **THEN** 입력한 글자가 남아 있다

#### Scenario: 입력 직후 다른 노트로 이동
- **WHEN** 사용자가 노트 A에 글자를 입력하고 곧바로 노트 B를 연다
- **THEN** 노트 A의 편집이 바로 저장되고, 다시 노트 A를 열면 "저장됨"이 보인다

#### Scenario: 저장 단축키
- **WHEN** 사용자가 원문을 입력하는 도중 `Cmd+S` 또는 `Ctrl+S`를 누른다
- **THEN** 편집이 바로 저장되어 "저장됨"이 보이고 브라우저의 페이지 저장 창은 열리지 않는다

### Requirement: 저장 상태 전이
각 노트의 저장 상태는 다음 규칙을 따라야 한다(SHALL). 저장을 기다리는 편집이 있거나 저장이 진행 중이면 "저장 중", 마지막 편집까지 모두 저장되면 "저장됨", 마지막 저장 시도가 실패했으면 "저장 안 됨"이다. 저장이 진행되는 동안 새로 입력하면 그 입력까지 저장될 때까지 "저장 중"을 유지해야 한다(MUST). 앱을 연 직후 불러온 노트는 "저장됨"이다.

#### Scenario: 입력부터 저장 완료까지
- **WHEN** 사용자가 "저장됨" 상태인 노트의 원문에 글자를 입력한다
- **THEN** 저장 상태가 "저장 중"으로 바뀐다
- **WHEN** 입력을 멈추고 저장이 끝난다
- **THEN** 저장 상태가 "저장됨"으로 바뀐다

#### Scenario: 노트별 상태
- **WHEN** 노트 A의 저장이 실패해 "저장 안 됨"인 상태에서 사용자가 편집하지 않은 노트 B를 연다
- **THEN** 노트 B는 "저장됨"으로 보인다
- **WHEN** 다시 노트 A를 연다
- **THEN** 노트 A는 "저장 안 됨"으로 보인다

### Requirement: 쓰기 실패 처리
저장소 용량 초과, 브라우저 설정으로 인한 저장소 차단 등으로 저장에 실패하면 해당 노트의 저장 상태를 "저장 안 됨"으로 표시해야 한다(SHALL). 실패해도 편집한 원문은 현재 세션에서 사라지지 않아야 하며(MUST NOT be lost), 사용자가 그 노트를 다시 편집하거나 즉시 저장 계기가 생기면 저장을 다시 시도해야 한다(SHALL). 앱을 열 때 저장소를 읽을 수 없으면 목업 노트로 화면을 표시하고, 편집은 가능하되 저장 시도는 실패로 표시해야 한다(SHALL).

#### Scenario: 용량 초과
- **WHEN** 저장소 용량이 가득 찬 상태에서 사용자가 원문을 편집한다
- **THEN** 저장 상태가 아이콘과 "저장 안 됨" 문구로 danger 색으로 보인다
- **AND** 원문과 미리보기에는 편집한 내용이 그대로 남아 있다

#### Scenario: 실패 뒤 재시도 성공
- **WHEN** 저장이 실패한 뒤 저장소에 여유가 생기고 사용자가 같은 노트에 글자를 하나 더 입력한다
- **THEN** 저장 상태가 "저장 중"을 거쳐 "저장됨"이 되고, 새로고침하면 실패 전 편집까지 모두 남아 있다

#### Scenario: 저장소를 쓸 수 없는 환경
- **WHEN** 브라우저 설정으로 사이트 저장소가 차단된 상태에서 앱을 연다
- **THEN** 목업 노트가 목록에 보이고 노트를 열어 편집할 수 있다
- **AND** 편집하면 저장 상태가 "저장 안 됨"이 된다

### Requirement: 손상되거나 알 수 없는 저장 데이터
저장된 노트 데이터 중 읽을 수 없거나 형식이 맞지 않거나 이 앱이 모르는 저장 형식 버전인 항목은 건너뛰고, 나머지 노트는 정상적으로 불러와야 한다(SHALL). 건너뛴 항목을 지우거나 덮어쓰지 않아야 한다(MUST NOT).

#### Scenario: 노트 하나가 손상됨
- **WHEN** 저장된 노트 7개 중 1개의 데이터가 손상된 상태에서 앱을 연다
- **THEN** 나머지 6개 노트가 목록에 보이고 열어 편집할 수 있다
- **AND** 손상된 항목의 저장 데이터는 그대로 남아 있다
