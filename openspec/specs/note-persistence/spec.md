# note-persistence Specification

## Purpose

노트 원문과 수정 시각을 사용자의 브라우저에 자동으로 저장해, 새로고침하거나 창을 다시 열어도 편집한 내용이 남아 있게 한다. 저장 시점, 저장 상태 전이, 실패와 손상된 데이터 처리를 정의한다.

## Requirements

### Requirement: 편집한 노트는 새로고침 후에도 유지
저장이 끝난 노트의 원문과 수정 시각은 같은 브라우저에서 새로고침하거나 창을 닫았다 다시 열어도 그대로 복원되어야 한다(SHALL). 제목, 미리보기 문장, 미리보기는 복원된 원문에서 다시 파생한다. 노트 데이터는 사용자의 브라우저 안에만 저장하며, 저장을 위해 네트워크 요청을 보내지 않아야 한다(MUST NOT).

#### Scenario: 새로고침 후 편집 유지
- **WHEN** 사용자가 노트 A의 원문 끝에 `## 새 섹션`을 입력하고 저장 상태가 "저장됨"이 된 뒤 페이지를 새로고침한다
- **THEN** 노트 A를 열면 원문과 미리보기에 "새 섹션"이 그대로 있다
- **AND** 목록에서 노트 A 카드의 제목과 미리보기 문장이 편집한 원문을 반영한다

#### Scenario: 저장 중 네트워크 요청 없음
- **WHEN** 사용자가 원문을 편집하고 저장이 일어난다
- **THEN** 저장을 위한 네트워크 요청이 발생하지 않는다

### Requirement: 첫 실행 초기 데이터
저장된 노트가 하나도 없는 상태로 앱을 열면 노트가 없는 빈 상태로 시작해야 하며(SHALL), 앱이 스스로 노트를 만들거나 저장소에 기록하지 않아야 한다(MUST NOT). 저장된 노트 항목이 있으면(이전 버전이 첫 실행 때 기록한 예시 노트 포함) 저장본을 그대로 사용해야 한다(MUST).

#### Scenario: 처음 연 앱
- **WHEN** 저장된 노트가 없는 브라우저에서 앱을 연다
- **THEN** 목록에 노트가 없고 노트 없음 빈 상태가 보인다
- **AND** 브라우저 저장소에 노트 레코드가 기록되지 않는다

#### Scenario: 저장본이 목업보다 우선
- **WHEN** 이전 버전에서 첫 실행 때 기록된 예시 노트들이 저장된 브라우저에서 앱을 연다
- **THEN** 그 노트들이 목록에 보이고 열어서 편집하거나 삭제할 수 있다

### Requirement: 자동 저장 시점
원문을 편집하면 별도 조작 없이 저장되어야 한다(SHALL). 입력이 약 0.5초 멈추면 저장하고, 멈추지 않고 계속 입력하는 동안에도 약 2초마다 한 번은 저장해야 한다(SHALL). 노트마다 따로 저장하며, 한 노트의 저장이 다른 노트의 원문이나 저장 상태를 바꾸지 않아야 한다(MUST NOT).

#### Scenario: 입력을 멈추면 저장
- **WHEN** 사용자가 원문에 글자를 입력하고 1초 동안 아무것도 입력하지 않는다
- **THEN** 저장 상태가 "저장됨"이 되고, 이때 새로고침하면 입력한 글자가 남아 있다

#### Scenario: 계속 입력해도 주기적으로 저장
- **WHEN** 사용자가 5초 동안 쉬지 않고 원문에 입력한다
- **THEN** 입력이 끝나기 전에도 저장이 일어나, 그 사이 새로고침하면 적어도 약 2초 전까지 입력한 내용은 남아 있다

### Requirement: 즉시 저장 계기
저장을 기다리는 편집이 있을 때 다음 경우에는 대기 시간을 기다리지 않고 바로 저장해야 한다(SHALL): 탭이나 창이 가려질 때, 페이지를 떠날 때, 다른 노트를 열거나 노트 선택을 벗어날 때, 사용자가 `Cmd+S`(macOS) 또는 `Ctrl+S`를 누를 때. 저장 단축키는 브라우저의 "페이지 저장" 동작을 열지 않아야 한다(MUST NOT).

#### Scenario: 입력 직후 탭 닫기
- **WHEN** 사용자가 원문에 글자를 입력하고 곧바로 탭을 닫은 뒤 앱을 다시 연다
- **THEN** 입력한 글자가 남아 있다

#### Scenario: 입력 직후 다른 노트로 이동
- **WHEN** 사용자가 노트 A에 글자를 입력하고 곧바로 노트 B를 연다
- **THEN** 노트 A의 편집이 바로 저장되고, 다시 노트 A를 열면 "저장됨"이 보인다

#### Scenario: 저장 단축키
- **WHEN** 사용자가 원문을 입력하는 도중 `Cmd+S` 또는 `Ctrl+S`를 누른다
- **THEN** 편집이 바로 저장되어 "저장됨"이 보이고 브라우저의 페이지 저장 창은 열리지 않는다

### Requirement: 새 노트의 첫 기록 시점
새로 만든 노트는 원문에 공백·줄바꿈이 아닌 글자가 처음 들어갈 때까지 저장소에 기록하지 않아야 한다(MUST NOT). 이 상태의 노트를 "기록 전 새 노트"라 하며, 저장 상태는 "저장됨"으로 표시한다. 공백이 아닌 글자가 처음 들어가면 그때부터 일반 노트와 같은 자동 저장 규칙을 따르며, 이후 원문을 모두 지워도 다시 기록 전 새 노트가 되지 않는다(MUST NOT). 새 노트의 레코드는 첫 기록 시점에 그 노트에 붙어 있는 태그(`note-tags` capability에 따라 태그 범위에서 만들었거나 기록 전에 붙이고 뗀 결과)를 붙인 순서대로 갖고, 폴더는 첫 기록 시점의 소속 폴더(`note-folders` capability에 따라 만든 범위나 사용자가 고른 폴더, 없으면 폴더 없음)로 기록한다.

#### Scenario: 입력 전에는 기록하지 않음
- **WHEN** 사용자가 "새 노트"를 누르고 아무것도 입력하지 않는다
- **THEN** 브라우저 저장소에 새 노트 레코드가 없다
- **AND** 저장 상태가 아이콘과 "저장됨" 문구로 보인다

#### Scenario: 첫 입력부터 자동 저장
- **WHEN** 사용자가 새 노트에 `# 장보기`를 입력하고 1초 동안 기다린다
- **THEN** 저장 상태가 "저장 중"을 거쳐 "저장됨"이 되고, 새로고침하면 목록에 "장보기" 노트가 있다

#### Scenario: 폴더에서 만든 새 노트의 기록
- **WHEN** 사용자가 "업무"를 보는 중에 새 노트를 만들어 `# 장보기`를 입력하고 1초 동안 기다린 뒤 새로고침한다
- **THEN** "업무"를 고르면 목록에 "장보기" 노트가 있다

#### Scenario: 입력 직후 탭 닫기
- **WHEN** 사용자가 새 노트에 글자를 입력하고 곧바로 탭을 닫은 뒤 앱을 다시 연다
- **THEN** 목록에 그 노트가 입력한 내용과 함께 있다

#### Scenario: 태그 범위에서 만든 새 노트의 기록
- **WHEN** 사용자가 "#회의" 범위를 보는 중에 새 노트를 만들어 "할 일" 태그를 더 붙이고 `# 장보기`를 입력한 뒤 1초 동안 기다리고 새로고침한다
- **THEN** "장보기" 카드에 "회의", "할 일" 칩이 그 순서로 보인다

### Requirement: 저장 상태 전이
각 노트의 저장 상태는 다음 규칙을 따라야 한다(SHALL). 저장을 기다리는 편집이 있거나 저장이 진행 중이면 "저장 중", 마지막 편집까지 모두 저장되면 "저장됨", 마지막 저장 시도가 실패했으면 "저장 안 됨"이다. 저장이 진행되는 동안 새로 입력하면 그 입력까지 저장될 때까지 "저장 중"을 유지해야 한다(MUST). 앱을 연 직후 불러온 노트는 "저장됨"이다.

#### Scenario: 입력부터 저장 완료까지
- **WHEN** 사용자가 "저장됨" 상태인 노트의 원문에 글자를 입력한다
- **THEN** 저장 상태가 "저장 중"으로 바뀐다
- **WHEN** 입력을 멈추고 저장이 끝난다
- **THEN** 저장 상태가 "저장됨"으로 바뀐다

#### Scenario: 노트별 상태
- **WHEN** 노트 A의 저장이 실패해 "저장 안 됨"인 상태에서 사용자가 편집하지 않은 노트 B를 연다
- **THEN** 노트 B는 "저장됨"으로 보인다
- **WHEN** 다시 노트 A를 연다
- **THEN** 노트 A는 "저장 안 됨"으로 보인다

### Requirement: 쓰기 실패 처리
저장소 용량 초과, 브라우저 설정으로 인한 저장소 차단 등으로 저장에 실패하면 해당 노트의 저장 상태를 "저장 안 됨"으로 표시해야 한다(SHALL). 실패해도 편집한 원문은 현재 세션에서 사라지지 않아야 하며(MUST NOT be lost), 사용자가 그 노트를 다시 편집하거나 즉시 저장 계기가 생기면 저장을 다시 시도해야 한다(SHALL). 앱을 열 때 저장소를 읽을 수 없으면 노트가 없는 빈 상태로 화면을 표시하고, 새 노트를 만들어 편집할 수 있되 저장 시도는 실패로 표시해야 한다(SHALL).

#### Scenario: 용량 초과
- **WHEN** 저장소 용량이 가득 찬 상태에서 사용자가 원문을 편집한다
- **THEN** 저장 상태가 아이콘과 "저장 안 됨" 문구로 danger 색으로 보인다
- **AND** 원문과 미리보기에는 편집한 내용이 그대로 남아 있다

#### Scenario: 실패 뒤 재시도 성공
- **WHEN** 저장이 실패한 뒤 저장소에 여유가 생기고 사용자가 같은 노트에 글자를 하나 더 입력한다
- **THEN** 저장 상태가 "저장 중"을 거쳐 "저장됨"이 되고, 새로고침하면 실패 전 편집까지 모두 남아 있다

#### Scenario: 저장소를 쓸 수 없는 환경
- **WHEN** 브라우저 설정으로 사이트 저장소가 차단된 상태에서 앱을 연다
- **THEN** 목록에 노트 없음 빈 상태가 보이고 새 노트를 만들어 편집할 수 있다
- **AND** 새 노트에 글자를 입력하면 저장 상태가 "저장 안 됨"이 된다

### Requirement: 노트 삭제
노트를 삭제하면 그 노트의 저장 레코드를 저장소에서 지워야 하며(SHALL), 지운 노트는 새로고침하거나 창을 다시 열어도 돌아오지 않아야 한다(MUST NOT). 삭제 전에 그 노트의 저장 대기나 진행 중인 저장이 있었다면, 삭제 뒤에 그 저장이 레코드를 다시 만들지 않아야 한다(MUST NOT). 저장소에서 지우기에 실패하면 노트는 화면과 저장본에 그대로 남고 실패가 삭제를 요청한 화면에 전달되어야 한다(SHALL). 기록 전 새 노트를 정리할 때는 저장소를 건드리지 않는다. 다른 노트의 원문과 저장 상태는 삭제의 영향을 받지 않아야 한다(MUST NOT).

#### Scenario: 삭제 후 새로고침
- **WHEN** 사용자가 노트 A를 삭제한 뒤 페이지를 새로고침한다
- **THEN** 목록에 노트 A가 없다

#### Scenario: 입력 직후 삭제
- **WHEN** 사용자가 노트 A에 글자를 입력하고 저장 상태가 "저장 중"일 때 곧바로 노트 A를 삭제한 뒤 2초 기다렸다가 새로고침한다
- **THEN** 목록에 노트 A가 없다

#### Scenario: 마지막 노트까지 삭제
- **WHEN** 사용자가 모든 노트를 삭제한 뒤 새로고침한다
- **THEN** 목록이 비어 있고 노트 없음 빈 상태가 보인다

#### Scenario: 지우기 실패
- **WHEN** 저장소에서 지우기가 실패한다
- **THEN** 노트가 목록에 그대로 있고, 새로고침해도 노트가 있다

### Requirement: 손상되거나 알 수 없는 저장 데이터
저장된 노트 데이터 중 읽을 수 없거나 형식이 맞지 않거나 이 앱이 모르는 저장 형식 버전인 항목은 건너뛰고, 나머지 노트는 정상적으로 불러와야 한다(SHALL). 건너뛴 항목을 지우거나 덮어쓰지 않아야 한다(MUST NOT). 폴더 항목도 같은 규칙을 따르며, 노트 항목과 폴더 항목은 서로의 손상에 영향을 받지 않아야 한다(MUST NOT).

#### Scenario: 노트 하나가 손상됨
- **WHEN** 저장된 노트 7개 중 1개의 데이터가 손상된 상태에서 앱을 연다
- **THEN** 나머지 6개 노트가 목록에 보이고 열어 편집할 수 있다
- **AND** 손상된 항목의 저장 데이터는 그대로 남아 있다

#### Scenario: 손상된 폴더를 가리키는 노트
- **WHEN** 노트 A가 속한 폴더의 저장 데이터가 손상된 상태에서 앱을 연다
- **THEN** 노트 A는 "폴더 없음"으로 보이고 열어 편집할 수 있다
- **AND** 노트 A를 편집해 저장해도 저장본의 폴더 값과 손상된 폴더 데이터는 그대로다
